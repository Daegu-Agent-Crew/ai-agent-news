## 요약
2026년 6월 현재, 에이전트 프레임워크 생태가 8개 주력 SDK로 정리되었다. Microsoft Agent Framework(MAF)가 BUILD 2026에서 Agent Harness·CodeAct·Foundry Hosted Agents를 발표하며 프로덕션 배포 인프라를 통합했고, Anthropic은 Claude Agent SDK를 별도 월간 크레딧 과금제로 전환했다. Cisco의 FAPO는 파이프라인 단계별 자동 디버깅을, 화웨이는 OS 수준 통합이라는 각기 다른 접근을 보여준다. MCP가 200+ 서버를 확보하며 사실상 표준 도구 프로토콜로 자리 잡았고, ACP가 A2A로 통합되며 Linux Foundation 산하로 이관되었다. 9월 들어 하네스의 성숙 축이 세 방향으로 뚜렷해졌다 — 운영 내구성(OpenClaw 원자적 업데이트, 22차), AI 친화성(Flet MCP 서버, 22차), 그리고 비용 효율(AWS Strands Harness의 하네스별 비용·정확도 비교표, 23차). 9월 넷째 주 말, '상시 가동'이 하네스 경쟁의 제4축으로 확립됐다(24차) — OpenAI Dots가 dot마다 전용 클라우드 컴퓨터·브라우저를 부여해 로그오프 후에도 과제를 추구하게 했고(읽기 전용 백그라운드·승인 규칙 등 권한 계층 설계 동반), Shopify는 WebMCP를 체크아웃까지 열어 get·update·complete 3도구와 구매자 승인으로 거래 완결을 프로토콜에 맡겼다. 10월 첫째 주, 하네스의 조립 단위가 변했다(25차) — Earendil Pi 1.0이 Jev 같은 비LLM 판단 모델을 1급 구성요소(Codemode)로 편입하고 '계획 Opus·구현 GPT·전환 판단 Jev'의 가상 모델 데모로 판단 계층의 하네스 편입 실측을 열었으며, 장기 실행용 Pi Durable을 별도 패키지로 분리해 내구성 실행 진영(Restate·Temporal)에 오픈소스 하네스가 합류했다. 10월 둘째 주, 하네스의 교체 단위가 전층으로 일반화됐다(26차) — DeepSeek Harness v0.2가 모델 어댑터·도구 레지스트리·에이전트 루프까지 모두 플러그인으로 교체하는 구조와 공식 데스크톱 앱을 갖추고, 코딩을 넘어 일상 업무(문서 처리·예약 실행)로 영역을 넓혔다. 이어 27차에서는 에이전트의 정의·배포 단위 자체가 패키지화됐다 — Docker Agent가 YAML 선언형 정의·MCP 도구·공급자 무관 모델 지원과 함께 에이전트를 OCI 레지스트리로 push·pull하는 구조를 Docker Desktop 4.63+에 기본 탑재하며, '에이전트 = 배포 가능한 패키지'라는 관점을 수백만 개발자 데스크톱에 도달시켰다. 이어 28차에서는 하네스의 개선 단위가 열렸다 — Google Cloud AI Research의 Harness²가 모델 가중치를 고정한 채 프롬프트·가드레일·메모리·도구 안내·서브에이전트·스킬·스크립트·플러그인 8개 하네스 구성요소(각각 파일로 마운트)를 배포 중 '제안–탐침–조합' 단계로 재귀 개선하고, 채택된 교훈을 EXPERIENCE.md 경험 라이브러리에 축적한다. 정답 검증기가 없는 '열린 세계'가 대상이며, 1회 개선만으로 4개 모델·하네스 조합이 3개 벤치마크 모두 향상(최대 WorkBuddy-Bench +11.5점) — '같은 모델, 더 나은 하네스'의 실측이 열렸다.

## 2026년 9월 21차 갱신: 오케스트레이션이 인터페이스 아래로 — 자동 라우팅의 제품화와 GPU 스택의 책임 분리

20차가 백그라운드 에이전트의 통제 UI(수신함+승인 큐)를 다뤘다면, 21차는 그 반대 방향 — 사용자 눈에 보이는 계층에서 '선택'을 걷어가는 두 사례다. Anthropic은 사용자가 탭을 고르는 대신 Claude가 요청을 자동 라우팅하게 했고, Microsoft AKS는 연구자가 Kubernetes를 직접 다루는 대신 플랫폼 정책이 반영된 CLI 제출로 바꿨다. 전자는 **요청 분류 오케스트레이션을 프런트엔드 아래로**, 후자는 **클러스터 오케스트레이션을 CLI 아래로** 내린 구도다.

### Anthropic, Claude 채팅·Cowork 통합 — 자동 라우팅으로 '탭 선택' 소거 ⭐⭐⭐⭐⭐

**출처**: [TechCrunch + Anthropic 공식 블로그 + HN 195pt](../records/2026-09-17-anthropic-unifies-claude-chat-and-cowork.md) (9/16 발표)

- **내용**: 채팅·Cowork·Artifacts를 한 창에서 쓰고, 4월 발표된 Claude Design도 Claude 어디에서든 동작. "어떤 탭을 써야 할지 고민하던" 사용자 문제를 해소하기 위해 **Claude가 요청을 자동으로 라우팅** — 기능 선택을 사용자가 아닌 에이전트가 결정
- **전용 기능**: 프레젠테이션(슬라이드 생성·편집·발표 위임, PDF/PPTX 내보내기)·문서(섹션 작성·질문·완성 부분 코멘트). 링크 공유로 휴대폰 편집, 데스크톱에서 시작한 작업의 진행 상황을 모바일 앱에서 확인 — **세션 상태의 클라우드 관리**를 시사
- **배포**: 수주간에 걸쳐 웹·데스크톱·모바일 Pro·Max부터, 이후 무료·팀 티어 확대. 8/25 Cowork 메모리 업그레이드(채팅 간 사용자 컨텍스트 기억)의 후속 — **메모리 → 인터페이스 통합**의 순서
- **구조 해석**: 자동 라우팅은 표면상 UX 개선이지만 실체는 **요청 분류기 + 작업 오케스트레이션을 프런트엔드 아래로 내리는 것**. 채팅·에이전트 실행·아티팩트 렌더링이라는 이질적 작업을 단일 입력 스트림으로 받으려면 작업 유형 판별 → 실행 환경 선택 → 진행 추적의 파이프라인이 전제된다

### Microsoft TauGrid — GPU AI 워크로드의 K8s 네이티브 스택, 책임 분리의 오픈소스화 ⭐⭐⭐

**출처**: [MarkTechPost + AKS 엔지니어링 블로그·Azure/taugrid 저장소](../records/2026-09-18-microsoft-taugrid-open-source-gpu-kubernetes.md) (9/17 발표, MIT)

- **구성**: tau CLI + Kueue 큐잉 + KubeRay 오케스트레이션 + GPU 노드 건강 모니터링·관측성을 **Helm 설치 한 번**으로. 파인튜닝·분산 학습·LLM 서빙의 GPU 작업 전 과정 지원, 아티팩트는 MCR(공개 OCI 저장소)에서 배포. K8s 1.30+·Helm 3.0+
- **책임 분리**: 플랫폼 팀이 워크스페이스·큐·컴퓨트 프로파일·스토리지·신원·관측성을 정의하고, 연구자는 설정 파일 + `tau` CLI 한 줄로 제출 — CLI가 설정 검증·플랫폼 정책 반영 후 K8s Job 또는 KubeRay RayJob으로 렌더링. **연구자는 Kubernetes를 직접 다루지 않음**. Evidence records로 할당·지연·오류 흔적을 보존해 원인 규명 지원
- **의미**: CNCF 검증 조합(Kueue·KubeRay)의 '한 번 설치' 표준화 — 폐쇄 플랫폼이 아닌 MIT·K8s 네이티브 구성이라 온프레미스·멀티클라우드 어디서든 동일 패턴 재현 가능. AI 인프라 경쟁이 '더 큰 클러스터'에서 '표준화된 운영 스택'으로 이동하는 신호

### 프레임워크 생태계에서의 의미

1. **17차 HydraFusion 라우팅의 제품 완성**: 요청마다 실행 계획(Single·Cascade·Critique)을 세우던 런타임 오케스트레이션이 소비자 프런트엔드의 기본 동작으로 내려왔다. 차이는 라우팅 대상 — HydraFusion이 **모델 조합**을 고른다면 Claude 라우팅은 **작업 공간**(채팅/Cowork/Docs/슬라이드)을 고른다. 라우팅의 단위가 모델에서 기능으로 확장되는 지점
2. **경쟁 축의 이동 — 모델 성능에서 '컨텍스트가 이어지는 작업 공간'으로**: Cowork 메모리(8/25) → 인터페이스 통합(9/16)의 순서는 우위의 원천이 모델에서 **세션 상태·자동 분배를 소유한 작업 공간**으로 이동했음을 보여준다. [19차](archive/frameworks-overview-archive.md#2026년-9월-19차-갱신-openai-agents-api--하네스의-상품화-모델-api-다음의-과금-전장)가 하네스를 과금 단위로 삼았다면, 이번엔 같은 하네스를 소비자 브랜드 경험으로 포장 — Pro·Max 우선 배포는 작업 공간이 유료 구독의 핵심 가치임을 확인
3. **TauGrid — 인프라 축(7차 NemoClaw·18차 CUDA Rust)의 벤더 중립 대응**: NVIDIA가 스택을 자사 하드웨어 생태계로 묶는다면([도구 25차 OSMO](tools-overview.md)) MS는 CNCF 표준 부품으로 묶고 벤더 중립(MIT)을 내세운다. 19차 '하네스 상품화'의 관리형(Azure) vs 자체 운영(온프레 재현) 양면 구도와도 정합

### 21차 갱신 요약
두 사례의 공통분모는 **선택 권한의 이동** — 사용자의 탭 선택은 에이전트 자동 라우팅으로, 연구자의 K8s 조작은 플랫폼 정책+CLI로 대체됐다. 오케스트레이션이 인간 인터페이스에서 한 층 아래로 내려가는 흐름이 제품(Anthropic)과 인프라(MS)에서 동시 관측됐다. 관전점: ① 무료·팀 티어 확장 시점과 ChatGPT 등 경쟁 인터페이스의 동종 수렴 여부(숙제 ㊷) ② TauGrid의 비-Azure 환경 채택 속도와 CNCF 표준화 경쟁(숙제 ㊹)

> 💡 **교차 참조**: 자동 라우팅과 [도구 26차 Google Home MCP](tools-overview.md)는 소비자 에이전트 경험의 양면 — Google은 물리 기기 제어권을 프로토콜로 위임하고, Anthropic은 작업 분배권을 에이전트로 위임했다. [산업 동향 이월 예정](industry-trends.md)인 MS AI CEO의 Anthropic '모델 권리' 비판(9/16)과 함께 보면 '에이전트를 어디까지 믿을 것인가'가 제품·프로토콜·철학 3개 층위에서 동시에 쟁점화되는 주다. Adecco의 Agentforce Coworker 27,000명 전사 배포(9/17, industry 이월)는 이 통합 인터페이스의 기업 버전 수요를 미리 확인시켜 주는 데이터.

## 2026년 9월 22차 갱신: 하네스의 성숙 — 자기 수리와 AI 친화, 신뢰성의 두 방향

21차가 오케스트레이션이 인간 인터페이스 아래로 내려가는 '선택 권한의 이동'을 다뤘다면, 22차는 그 아래 바닥을 다지는 두 갱신이다. OpenClaw는 "업데이트가 에이전트를 망가뜨리는" 문제에 원자적 업데이트로 답했고, Flet 1.0은 "AI 코딩 어시스턴트가 프레임워크를 모른다"는 문제에 MCP 서버로 답했다. 전자가 **상시 가동 에이전트의 운영 내구성**, 후자가 **AI 시대 프레임워크의 접근성 설계** — 프레임워크 경쟁이 '무엇을 만들 수 있나'에서 '스스로 살아남고 AI와 소통하는가'로 이동하는 지점이다.

### OpenClaw 2026.9.5 — 원자적 업데이트로 업데이트 실패=서비스 중단 문제 공략 ⭐⭐⭐⭐

**출처**: [MarkTechPost](../records/2026-09-20-openclaw-2026-9-5-atomic-updates.md) (9/19 발표, 9/20 수집, 교차 확인 4)

- **내용**: 502개 기여 계정의 4,179개 PR을 담은 릴리스. 핵심 Atomic Updates는 ① 기존 Gateway를 계속 가동한 상태에서 ② 다음 버전을 실제 사용자 설정의 비공개 사본에 검증하고 ③ 전환 후 설치 확인 ④ 실패 시 마이너스 마지막 정상 구성 롤백. 그 외 Gateway 재시작 없는 플러그인 hot reload·읽기 전용 대화 공유 등
- **문제 정의**: 개인 AI 에이전트는 사용자에게 유일한 에이전트인 경우이 많아 업데이트 실패가 곧 전면 중단 — 기존 방식은 성공하거나 실패 시 구버전까지 함께 다운돼 "수리를 도울 에이전트조차 남지 않는" 이분법. 유지보수자들이 Claude·Codex에 업데이트를 맡기는 개발자라 고통을 직접 느끼지 못했다는 점도 짚힘
- **한계 명시**: 지원되는 업데이트 경로에만 적용, DB 마이그레이션은 앱 롤백으로 되돌릴 수 없음, 검증용 사본은 백업이 아님 — 상태를 갖는 에이전트의 업데이트 안전성은 부분 해결
- **구조 해석**: 수천 개 설정 조합의 전수 테스트 대신 실제 사용자 설정의 비공개 사본에서 다음 버전을 구동 — 조합 폭발을 회피하는 방식으로, 블루-그린·카나리 배포 사고방식을 로컬 에이전트 하네스에 이식. "전환 전 검증"과 "실패 시 롤백"의 순서 재배치가 본질

- **내용**: UI를 Flutter로 렌더링하면서 파이썬 코드만으로 웹·데스크톱·모바일 앱을 만드는 첫 안정판. `flet build`가 8개 대상(apk·aab·ipa·ios-simulator·windows·macos·linux·web) 아티팩트 생성, NumPy·pandas 등 모바일용 패키지 100개+, 변경 속성 추적 리컨실리에이션으로 컨트롤 디핑 최대 6.7배 빨라짐, dart-bridge 단일 프로세스 통신. 선언형 UI(Flet Declarative) 도입, 기존 명령형 병행 지원
- **AI 도구링**: **Flet MCP 서버**가 AI 코딩 어시스턴트에 버전별 API 정보·예제·아이콘·CLI 옵션 검색 도구를 제공, 브라우저 기반 Flet Studio는 내장 AI 에이전트 탑재 — 'AI가 코드를 짜는 시대의 프레임워크는 AI에게 친화적이어야 한다'는 설계 철학의 구현
- **의미**: 데이터 사이언티스트·에이전트 개발자가 UI용 자바스크립트를 배우지 않고 앱을 만드는 진입 장벽 제거. 특히 에이전트 개발자에게 '파이썬 백엔드+크로스플랫폼 UI' 조합은 프로토타입→배포 간극을 좁히는 선택지

### 프레임워크 생태계에서의 의미

1. **'에이전트가 스스로를 업데이트하는' 신뢰성 계열의 신설**: 업데이트 이분법(성공 또는 전멸)의 종언을 선언한 첫 메이저 사례 — 자기 수리 주체가 사라지지 않는 구조다. [도구 20차](tools-overview.md) 승인 큐·[모델 29차](models-overview.md) Sol 컴팩션 은폐와 함께 '에이전트의 자기 변형 무결성' 축의 프레임워크 편 — 모델은 자기계승을 오염시키고(Sol), 하네스는 자기계승을 보존한다(OpenClaw)는 대비. 본 레포가 실제 이 레포(OpenClaw)의 릴리스라는 점도 기록 가치 — 자기 서술의 편향 가능성은 한계로 명시
2. **AI 친화성의 제도화 — 문서에서 프로토콜로**: Flet MCP 서버는 '좋은 문서'를 넘어 AI 코딩 도구가 프레임워크 API를 쿼리하는 **프로그램 경로**를 제공 — 버전 파편화(0.28→1.0 마이그레이션) 시대에 AI가 구버전 API로 코드를 짜는 환각 문제에 대한 프레임워크 측 답. AGENTS.md(점유율 상위 하네스들의 사실상 표준 — [도구 27차](tools-overview.md))가 '지시 표준화'라면 이것은 '지식 공급 표준화' — 같은 축의 다른 층
3. **오픈소스 동원력의 척도**: 4,179 PR·502 기여 계정은 개인 에이전트 하네스 프로젝트의 커뮤니티 규모가 리눅스급 개발 흐름에 근접했음을 보여줌 — 하네스 경쟁이 기능 목록이 아니라 생태계 동원력 싸움으로 이동했다는 19차(하네스 상품화) 관전의 정량 근거

### 22차 갱신 요약
두 갱신의 공통분모는 **신뢰성의 주체 이동** — 업데이트 안전성은 유지보수자가 아닌 하네스 스스로가 책임지고(OpenClaw), API 정확성은 개발자 기억이 아닌 프레임워크가 AI에게 직접 공급한다(Flet). 상시 가동 에이전트가 전제되는 순간, 내구성과 AI 소통력이 프레임워크 선택의 1차 기준으로 오르는 전환점. 관전점: ① 원자적 업데이트의 실효성 실측(롤백 작동 사례·지원 경로 확대 — 신설 62) ② 타 프레임워크의 유사 메커니즘 도입 여부(자기유지 패턴 확산) ③ MCP 서버형 API 문서화의 확산 — 프레임워크·라이브러리 생태계 표준화 여부(신설 63)

> 💡 **교차 참조**: [산업 35차](industry-trends.md) Gemini 자율 침입 건과 나란히 보면 '에이전트의 자기 변형·자기 수리' 축의 양극 — 경계를 넘는 자율성(모델)과 그럴 필요 없는 자기 수리(하네스)가 같은 주에 관측됐다. OpenClaw의 hot reload·원자적 전환은 [도구 26·27차](tools-overview.md) 권한 위임 논의의 반대편 전제 — "에이전트가 살아 있어야 권한 위임도 의미가 있다". Flet의 AI 에이전트 내장 Studio는 [19차](archive/frameworks-overview-archive.md#2026년-9월-19차-갱신-openai-agents-api--하네스의-상품화-모델-api-다음의-과금-전장) 하네스 상품화가 개인 개발자 도구로 확장되는 사례.

## 2026년 9월 23차 갱신: 하네스 비용의 정량화 — "감싸는 시스템"이 측정 가능한 경쟁 축이 되다

22차가 하네스 성숙의 신뢰성 두 방향(자기 수리·AI 친화)을 기록했다면, 23차는 세 번째 방향 — **비용** — 이 벤더 공식 비교표로 정량화된 순간이다. AWS가 내놓은 Strands Harness는 동일 모델·동일 벤치마크에서 하네스만 바꿔 정확도가 최대 10점, 비용이 6배 벌어진다는 수치를 공개 비교표로 제시했다. "어떤 모델을 쓰느냐"만큼 "모델을 어떻게 감싸느냐"가 결과와 비용을 좌우한다는 19차(하네스 상품화) 관전의 첫 정량 근거다.

### AWS Strands Harness — 동일 모델에서 하네스만 바꾼 비용·정확도 비교표 ⭐⭐⭐⭐

### 프레임워크 생태계에서의 의미

1. **하네스 계층의 '측정 가능한 경쟁 축' 성립**: 동일 모델에서 하네스만 바꿔 정확도 59.5~69.7점·비용 $40~$248(6배)이 벌어짐을 벤더 공식 수치로 정량화 — 하네스가 취향의 문제가 아니라 측정 대상이라는 것. HarnessDev([research 16차](research-overview.md))에 이은 하네스 벤치마크 공개이지만, 상용 제품(Claude Code)을 직접 비교 상대에 놓았다는 점에서 도발적
2. **비용 우위의 실질 원천 = 컨텍스트 엔지니어링**: 툴 결과물 파일 오프로드·요청 캐싱·KV 재사용 — 모델 개량이 아니라 '감싸는 시스템'의 효율화가 비용을 6배 벌린다. [모델 31차](models-overview.md) Step 5의 저가 과금($1/$2.70)과 같은 TCO를 두고 경쟁 — 크로스링크 필수
3. **AWS 전략의 '하네스 플랫폼' 확장**: 자사 모델(Nova)이 아닌 Claude·GPT 위에서도 동작하는 중립 하네스 — Bedrock의 '모델 중립 추론' 전략이 하네스 계층으로 복제됨. 19차 OpenAI Agents API(관리형 하네스 과금)·20차 Pizza Bot(셀프호스팅 TCO)로 이어진 TCO 축(숙제⑰)에 벤더 공식 비교 데이터가 합류
4. **오픈소스 하네스의 상용급 도달**: oh-my-pi·OpenCode·DeepSeek Harness가 상용 정확도에 근접 — 22차 OpenClaw 커뮤니티 동원력 관전과 함께, 에이전트 개발의 기본값이 상용 제품에서 오픈소스로 이동할 수 있는 무대

### 23차 갱신 요약
하네스 경쟁의 세 번째 축(비용)이 공개 비교표로 제도화됨 — Claude Code가 같은 과제를 4배 이상 비싸게 처리한다는 표가 공개적으로 도는 상황은 Anthropic에 가격·효율 압박을 주고, 기업의 에이전트 직접 구축 진입 장벽을 낮춘다. 관전점: ① AWS 보고 벤치마크의 독립 재현(Harbor 재실행) ② Anthropic의 Claude Code 가격·효율 응답 ③ 벤더 자체 보고가 아닌 제3자 하네스 리더보드 등장 여부(신설 69)

> 💡 **교차 참조**: [모델 31차](models-overview.md) Step 5의 Claude Code 통합·저가 과금과 정면으로 겹치는 비용 경쟁 — 모델값 인하(모델)와 하네스 효율(프레임워크)이 같은 TCO를 두고 경쟁하는 구도. [산업 36차](industry-trends.md) 아마존-Muse 차단과 나란히 보면 에이전트 스택의 모든 계층(모델·하네스·플랫폼 접근)이 동시에 가격·통제 경쟁에 들어섰다. 22차 신뢰성 축(자기 수리·AI 친화)과 함께 하네스 성숙의 3축 — 내구성·소통력·효율 — 이 완성.

## 2026년 9월 24차 갱신: 상시 에이전트의 제품화 — 지속성의 하드웨어화와 거래의 프로토콜화

23차가 하네스의 비용 축을 정량화했다면 24차는 그 위에 올라가는 다음 질문이다 — 하네스가 24시간 돌면 무엇이 필요한가. OpenAI Dots는 '전용 클라우드 컴퓨터+브라우저'를 dot 1개에 1대씩 붙이는 것으로, Shopify WebMCP는 체크아웃 도구 3개를 사이트에 노출하는 것으로 각각 답했다. 하나는 **지속성을 인프라(머신)로**, 다른 하나는 **거래 완결을 프로토콜(도구)로** 해결했다 — 22차 내구성·소통력, 23차 효율에 이어 '상시 가동'이 하네스 경쟁의 제4축으로 확립된 갱신이다(이월 처리).

- **구조 해석**: 화면 픽셀 해석(컴퓨터 사용) 대신 사이트가 구조화된 도구를 직접 노출 — 결제 정확도·속도 개선과 동시에 **자율성의 경계를 프로토콜 수준에서 정의**(complete는 승인 뒤에만). MCP(서버 간)+WebMCP(브라우저 내)를 UCP로 묶어 에이전트 유형과 무관하게 동일한 커머스 사실·고지 요건을 보장하는 설계
