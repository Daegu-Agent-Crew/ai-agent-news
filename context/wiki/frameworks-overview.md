## 요약
2026년 6월 현재, 에이전트 프레임워크 생태가 8개 주력 SDK로 정리되었다. Microsoft Agent Framework(MAF)가 BUILD 2026에서 Agent Harness·CodeAct·Foundry Hosted Agents를 발표하며 프로덕션 배포 인프라를 통합했고, Anthropic은 Claude Agent SDK를 별도 월간 크레딧 과금제로 전환했다. Cisco의 FAPO는 파이프라인 단계별 자동 디버깅을, 화웨이는 OS 수준 통합이라는 각기 다른 접근을 보여준다. MCP가 200+ 서버를 확보하며 사실상 표준 도구 프로토콜로 자리 잡았고, ACP가 A2A로 통합되며 Linux Foundation 산하로 이관되었다. 9월 들어 하네스의 성숙 축이 세 방향으로 뚜렷해졌다 — 운영 내구성(OpenClaw 원자적 업데이트, 22차), AI 친화성(Flet MCP 서버, 22차), 그리고 비용 효율(AWS Strands Harness의 하네스별 비용·정확도 비교표, 23차). 9월 넷째 주 말, '상시 가동'이 하네스 경쟁의 제4축으로 확립됐다(24차) — OpenAI Dots가 dot마다 전용 클라우드 컴퓨터·브라우저를 부여해 로그오프 후에도 과제를 추구하게 했고(읽기 전용 백그라운드·승인 규칙 등 권한 계층 설계 동반), Shopify는 WebMCP를 체크아웃까지 열어 get·update·complete 3도구와 구매자 승인으로 거래 완결을 프로토콜에 맡겼다. 10월 첫째 주, 하네스의 조립 단위가 변했다(25차) — Earendil Pi 1.0이 Jev 같은 비LLM 판단 모델을 1급 구성요소(Codemode)로 편입하고 '계획 Opus·구현 GPT·전환 판단 Jev'의 가상 모델 데모로 판단 계층의 하네스 편입 실측을 열었으며, 장기 실행용 Pi Durable을 별도 패키지로 분리해 내구성 실행 진영(Restate·Temporal)에 오픈소스 하네스가 합류했다. 10월 둘째 주, 하네스의 교체 단위가 전층으로 일반화됐다(26차) — DeepSeek Harness v0.2가 모델 어댑터·도구 레지스트리·에이전트 루프까지 모두 플러그인으로 교체하는 구조와 공식 데스크톱 앱을 갖추고, 코딩을 넘어 일상 업무(문서 처리·예약 실행)로 영역을 넓혔다. 이어 27차에서는 에이전트의 정의·배포 단위 자체가 패키지화됐다 — Docker Agent가 YAML 선언형 정의·MCP 도구·공급자 무관 모델 지원과 함께 에이전트를 OCI 레지스트리로 push·pull하는 구조를 Docker Desktop 4.63+에 기본 탑재하며, '에이전트 = 배포 가능한 패키지'라는 관점을 수백만 개발자 데스크톱에 도달시켰다. 이어 28차에서는 하네스의 개선 단위가 열렸다 — Google Cloud AI Research의 Harness²가 모델 가중치를 고정한 채 프롬프트·가드레일·메모리·도구 안내·서브에이전트·스킬·스크립트·플러그인 8개 하네스 구성요소(각각 파일로 마운트)를 배포 중 '제안–탐침–조합' 단계로 재귀 개선하고, 채택된 교훈을 EXPERIENCE.md 경험 라이브러리에 축적한다. 정답 검증기가 없는 '열린 세계'가 대상이며, 1회 개선만으로 4개 모델·하네스 조합이 3개 벤치마크 모두 향상(최대 WorkBuddy-Bench +11.5점) — '같은 모델, 더 나은 하네스'의 실측이 열렸다. 이어 29차에서는 내구성이 하네스 바깥의 공통 계층으로 분리됐다 — Vercel이 durable-harness(npm·Apache-2.0·0.0.x)로 Pi·OpenCode·fx·Claude Code·Codex를 수정 없이 감싸고, 턴의 각 단계를 의도·결과 내구성 로그로 기록한 뒤 큐 기반 재개·토큰 이중 과금 방지·replay safe/never 멱등성 명시로 클라우드 상시 코딩 에이전트의 크래시 복구를 인프라 경쟁 포인트로 만들었다(29차). 이어 30차에서는 격리가 실행 계층으로 완성됐다 — NVIDIA OpenShell(Apache-2.0·0.1.x)이 자율 에이전트 무리를 격리 샌드박스에 두고 커널 계측으로 모든 파일 접근·시스템 콜·네트워크 연결에 정책을 강제하며, 에이전트는 실제 자격 증명을 보지 못하고 승인된 엔드포인트로 가는 요청에만 주입을 받으며, 정책 변경은 승인 전 형식 검증으로 위험한 신규 권한을 사전 점검한다(30차). 이어 31차에서는 조정의 위상 자체가 논쟁거리가 됐다 — Microsoft Research의 Agensh가 중앙 오케스트레이터 없이 모든 워커가 같은 5단계 루프(읽기→CLAIM 선점·DM 조정→작업·검증→공유 Git 병합)를 프롬프트 안에서 비동기 반복하는 분산 하네스를 MIT로 공개했고, ProgramBench 최난 5과제에서 1개→128개 에이전트 19.31%→28.78%(GPT-5.6-sol)·pandoc 1,024개 55.06%와 함께 규모별 창발(8개 인터페이스 합의→32개 상호 리뷰→1,024개 통합자 역할, 하드코딩 없음)을 관측했다 — 리드+서브에이전트 주류(Claude Code ## 2026년 9월 24차 갱신: 상시 에이전트의 제품화 — 지속성의 하드웨어화와 거래의 프로토콜화

23차가 하네스의 비용 축을 정량화했다면 24차는 그 위에 올라가는 다음 질문이다 — 하네스가 24시간 돌면 무엇이 필요한가. OpenAI Dots는 '전용 클라우드 컴퓨터+브라우저'를 dot 1개에 1대씩 붙이는 것으로, Shopify WebMCP는 체크아웃 도구 3개를 사이트에 노출하는 것으로 각각 답했다. 하나는 **지속성을 인프라(머신)로**, 다른 하나는 **거래 완결을 프로토콜(도구)로** 해결했다 — 22차 내구성·소통력, 23차 효율에 이어 '상시 가동'이 하네스 경쟁의 제4축으로 확립된 갱신이다(이월 처리).

### OpenAI Dots — dot마다 전용 클라우드 컴퓨터, 로그오프 후에도 과제를 추구하는 상시 에이전트 ⭐⭐⭐⭐⭐

### Shopify WebMCP 체크아웃 — get·update·complete 3도구로 결제 완결을 에이전트에 위임 ⭐⭐

**출처**: [TechCrunch](../records/2026-09-28-shopify-webmcp-checkout-ai-agents.md) (9/28 발표, 9/29 수집, 교차 확인 1)

- **내용**: 스토어프론트·장바구니에 이어 **Shop Pay 포함 체크아웃까지 WebMCP 확장**. get_checkout(조회)·update_checkout(주소·배송 옵션 변경)·complete_checkout(**구매자 승인 후** 주문 완성) 3도구로 에이전트가 스크린샷·스크래핑 없이 결제 화면을 읽고 수정·제출. 전 적격 가맹점에 자동 배포, 기존 서버 간 호스팅 MCP와 함께 UCP(Universal Commerce Protocol) 기반 — Muse·Instinct 직접 파트너십 동반
- **구조 해석**: 화면 픽셀 해석(컴퓨터 사용) 대신 사이트가 구조화된 도구를 직접 노출 — 결제 정확도·속도 개선과 동시에 **자율성의 경계를 프로토콜 수준에서 정의**(complete는 승인 뒤에만). MCP(서버 간)+WebMCP(브라우저 내)를 UCP로 묶어 에이전트 유형과 무관하게 동일한 커머스 사실·고지 요건을 보장하는 설계

### 프레임워크 생태계에서의 의미

1. **'상시 가동'이 하네스 성숙의 제4축으로**: 22차 내구성·소통력, 23차 비용에 이어 지속성(persistence)이 제품 요구사항으로 확립. dot의 전용 머신 할당은 [22차 OpenClaw 원자적 업데이트](#2026년-9월-22차-갱신-하네스의-성숙--자기-수리와-ai-친화-신뢰성의-두-방향)와 같은 '살아 있는 에이전트' 전제의 대형 사례 — OpenClaw가 자기 수리를 향했다면 Dots는 상시 작업 수행을 향한 차이
2. **권한 계층 설계의 소비자 규모 실측**: 읽기 전용 백그라운드·승인 요구 규칙·자격 증명 비노출은 [20차 승인 큐](#2026년-9월-20차-갱신-aws-pizza-bot--수신함승인-큐-통제-ui의-표준-경쟁)·[도구 27차](tools-overview.md) 권한 위임 UX(숙제 52)의 소비자 버전 구현. [산업 35차](industry-trends.md) Gemini 자율 침입·37차 메디케어 침입이 '권한을 준 만큼 표면이 커진다'는 반례였다면, Dots는 그 답으로 권한 단계 설계를 내건 셈 — 첫 대형 사고 시 어느 안전장치가 작동했는지가 판정 관문
3. **'소비자 에이전트 거래' 축의 프로토콜 편**: 아마존의 차단([산업 36차](industry-trends.md) 70)·구글의 플릿카트 직접 구매([산업 40차](industry-trends.md) 87)에 이어 Shopify는 '여는 쪽'의 프로토콜 답 제시 — complete를 승인 뒤에 묶은 설계는 차단과 무제한 위임 사이의 제3경로. WebMCP 제안 표준에 Shopify 규모 실측 데이터가 실리는 효과(숙제 70·87 통합 관전)

### 24차 갱신 요약
두 갱신의 공통분모는 **행동 반경을 늘리는 대신 그 경계를 구조(권한·프로토콜)로 같이 설계했다**는 것 — Dots는 권한 단계(읽기 전용 백그라운드·승인 규칙·자격 증명 격리), Shopify는 프로토콜 계약(승인 후 complete)으로 답했다. 관전점: ① dot의 TCO 실측 — 전용 컴퓨터×사용자 수의 인프라 비용과 $500 유료 등급 구성(⑰ TCO 축의 새 변수) ② 백그라운드 읽기 전용 강제의 우회 사례·첫 보안 사고 시 안전장치 작동 여부(숙제 52·83) ③ WebMCP 표준화 논의에서 Shopify 3도구의 원형 역할(숙제 87 확장)
