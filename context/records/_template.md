# 뉴스 Record 템플릿

## 파일명 규칙
`YYYY-MM-DD-{slug}.md` (예: `2026-06-23-claude-computer-use.md`)

## 구조

```markdown
# {뉴스 제목}

## 메타데이터
- **원문 URL**: {url}
- **소스**: {출처}
- **발행일**: YYYY-MM-DD
- **수집일**: YYYY-MM-DD
- **수집자**: {대구루|레노버}
- **카테고리**: {framework|model|tool|industry|research}
- **태그**: [태그1, 태그2]
- **소스 권위**: {official | major-media | community}
- **교차 확인**: {N} (독립 소스 개수, 단일이면 1)
- **중요도**: ⭐⭐⭐⭐⭐ (1~5, 아래 산정 규칙 필수)
- **신선도**: fresh | updated | stale (수집 시 fresh, 60일 후 stale)

## 핵심 요약
> {1-2문장 요약 — 사실 문장은 원문 발췌로 소급 가능해야 함}

## 번역 (한국어)
{핵심 내용 한국어 번역, 3~5문단}

## 왜 중요한가?
{이 뉴스가 왜 중요한지 2~3문장으로 설명. 비기술자도 이해할 수 있게.}

## 심층 분석

### 기술 의미
{이 뉴스의 기술적 의미, 최소 3문장}

### 업계 영향
{AI 에이전트 생태계에 미치는 영향, 최소 3문장}

### 관련 프로젝트
- {관련 링크/프로젝트}

### 관련 뉴스
- [제목](../records/{파일명}.md) — {한 줄 설명}

## 원문 발췌
> {요약의 핵심 사실을 지지하는 영어 원문 문장, 2~4문장. 저작권 범위 내}

## 수집 노트
- **선정 이유**: {같은 탐색의 후보 중 이 뉴스를 아카이브한 이유 1문장 — 소스 권위·교차 확인과 연결}
- **제외 후보**: {버린 후보와 이유 1~2개. 예: "GPT-5.5 벤치마크 재보도 — 주요 소스 1건으로 중복 정리 완료". 없으면 "없음"}
```

## 증거 규칙 (관찰/판단 분리)

**확신에 찬 오류가 빈 칸보다 나쁘다.** 다음 세 가지만 지키면 된다.

1. **사실은 소급 가능하게** — 핵심 요약·번역의 사실 문장(수치, 발표, 날짜, 인용)은 원문 발췌로 거슬러 올라갈 수 있어야 한다. 소급 불가능한 주장은 심층 분석으로 이동하거나 문장 끝에 `(→ 분석)`을 붙인다.
2. **주장은 속성과 함께** — 타 매체·연구자의 주장을 전달할 때 "X가 주장/보고" 형태로 누구의 말인지 명시한다. 속성 없는 주장은 사실처럼 읽힌다.
3. **확신도 점수 금지** — "확실함/신뢰도 높음" 같은 자기 평가를 쓰지 않는다. 근거의 성격(공식 발표인가, 단일 커뮤니티 포스트인가)을 관찰로 적으면 독자가 판단한다.

## 중요도 산정 규칙

모델의 직감 대신 관찰 가능한 신호로만 계산한다. 기본 1점에서 시작해 합산, 최소 1 최대 5.

| 신호 | 관찰 기준 | 점수 |
| --- | --- | --- |
| 소스 권위 | official (공식 블로그·발표) | +2 |
| | major-media (TechCrunch 등 주요 언론) | +1 |
| | community (HN, Reddit, 개인 블로그) | +0 |
| 교차 확인 | 독립 소스 3개 이상 | +2 |
| | 독립 소스 2개 | +1 |
| 반응 규모 | 커뮤니티 유의미 반응 (예: HN 100pt+) | +1 |

예: 공식 발표 + 주요 언론 3곳 교차 = 1+2+2 = ⭐⭐⭐⭐⭐
예: 단일 커뮤니티 제보, 반응 미미 = 1 = ⭐

"업계에 미칠 영향이 크다" 같은 판단은 이 표의 입력이 아니라 심층 분석의 영역이다.

## 적용 기준

- **2026-09-11 이후 수집분**부터 소스 권위·교차 확인·수집 노트가 필수다.
- 이전 레코드는 소급 수정하지 않는다 (lint가 legacy 경고로만 표시).
